# @datatug/board-models

The DataTug ↔ Dashboardius board contract (Phase 3 enabler).

Founder direction (2026-09-08 Idea, verbatim): *"A Dashboardius board IS a
DataTug board; what Dashboardius adds is widget kinds and an editing
experience."* Founder ruling (2026-09-09, verbatim): *"board belongs to
DataTug project. Project can be shared across Sneat spaces."*

**DataTug owns the schema.** `Board`/`BoardRow`/`BoardCard`/`BoardWidget` and
the widget defs in this package are TypeScript types generated by hand from
`datatug-core/pkg/datatug/boards.go` (the Go source of truth), field for
field — matching JSON field names (`json:"..."` struct tags), not Go field
names. Nothing in this package executes a query, renders a widget, or owns
layout/editing — that stays in the DataTug server (persistence, execution,
access control) and in Dashboardius (presentation and editing) respectively.

**Dashboardius consumes it.** Dashboardius imports these types instead of
keeping its own copy of the board schema, so the two products can't drift
apart silently. See "What Dashboardius must change" below — this repo does
not modify `sneat-co/dashboardius`.

## What's in here

- `Board`, `BoardRow`, `BoardCard` — the board tree.
- `BoardWidget` — a card's widget (`name` + `data`, `data` stays `unknown`
  exactly like Go's `interface{}`, since which shape it holds depends on
  `name`).
- Widget defs: `SQLWidgetDef`/`SQLWidgetSettings`,
  `HTTPWidgetDef`/`HTTPRequest`/`HTTPHeaderItem`, `TabsWidgetDef`/`TabWidget`,
  plus the shared `WidgetBase` (`title`, `parameters`) they all inline (Go
  embeds `WidgetBase` anonymously, which JSON-inlines its fields — modelled
  here with `interface X extends WidgetBase`).
- `BOARD_WIDGET_NAME_SQL` / `_HTTP` / `_TABS` — the `BoardWidget.name` values
  `boards.go`'s `BoardWidget.Validate()` currently recognizes, plus the
  `BoardWidgetName` convenience union built from them.
- `BoardId`, `BoardCardId` — id aliases (Go: plain `string`).
- `ParameterLookup` — mirrors the struct of that name *declared inside*
  `boards.go` itself.
- `BOARD_MODELS_VERSION` — bump whenever a field is added, renamed or removed
  relative to `boards.go`, so a version-pinned consumer can detect drift.

### Scope boundary

`Board` embeds Go's generic `ProjectItem` → `ProjItemBrief` → `ListOfTags`
(`proj_item.go`, `tag.go`) — the project-item system shared by every DataTug
item kind (boards, queries, environments, ...), not just boards. Its JSON
fields (`id`, `title`, `folder`, `tags`, `userIds`, `access`) are flattened
directly onto `Board` here; the generic, importable `ProjectItem` hierarchy
itself is out of scope for this package, which is ONLY the board model
types per this package's brief.

Similarly, `WidgetBase.Parameters` is typed `Parameters` (`[]ParameterDef`)
in Go, but `ParameterDef` lives in `parameters.go` (not `boards.go`) and its
`Meta` field references `EntityFieldRef` from `entities.go`. Rather than pull
in that whole cross-cutting system, `src/lib/widget-parameter.ts` has a
minimal, self-contained, field-for-field copy (`BoardParameterDef`,
`BoardParameterFieldRef`) — just enough for the widget defs to be faithful.
If a `@datatug/parameter-models` (or similar) package is published later,
that copy should be replaced with an import from it.

## JSON-shape testing

`src/lib/__fixtures__/board.fixture.json` is a hand-written fixture exercising
every field and widget kind (SQL, HTTP, and a nested tabs widget with a SQL
tab and an HTTP tab), built from `boards.go`'s struct tags. `board.spec.ts`
asserts:

- `boardFixtureJson satisfies Board` — compile-time: the fixture's shape is
  assignable to the `Board` type (catches added/renamed/removed fields at
  `nx build`/typecheck time, not just in tests).
- a JSON round trip (`JSON.parse(JSON.stringify(board))`) reproduces the
  fixture exactly — no field is silently dropped or renamed by the TS shape.
- each widget kind narrows and reads correctly through nesting (tabs → SQL /
  tabs → HTTP), including `parameters[].meta` / `.lookup`.

## What Dashboardius must change

`sneat-co/dashboardius` was not available in this worktree's read-only
references at the time this package was written, so this is a contract-level
list, not a diff against its current code:

1. Add `@datatug/board-models` as a dependency (once CD publishes it — this
   package does not publish itself).
2. Replace its own copy of `Board`/`BoardRow`/`BoardCard`/`BoardWidget` (and
   any SQL/HTTP/tabs widget-def types it re-exported field-for-field per its
   `docs/IMPLEMENTATION-RECORD.md`) with imports from this package.
3. Keep its own widget *kinds* (chart widgets, layout, editing state) as
   Dashboardius-local types that reference `BoardWidget`/`BoardCard` from
   this package rather than redefining the board tree itself.
4. If Dashboardius's current widget-def shapes have already drifted from
   `boards.go` (extra fields, different nesting), that drift needs a
   reconciliation pass in Dashboardius's own repo — this package intentionally
   does not carry forward any Dashboardius-only fields.

## Reconciliation of `libs/datatug/main` (2026-09-09)

`libs/datatug/main/src/lib/models/definition/board/board.ts` and its sibling
`widget*.ts` files used to be a pre-existing, independently-evolved copy of
the board schema, not a re-export of `boards.go`. It has been reconciled to
consume this package; the local copy is gone.

### Verdict and evidence

Every field that had diverged from `boards.go` was dead or aspirational:

1. `IBoardDef.description` and `IBoardDef.related.boards` had zero readers
   anywhere in `libs/` or `apps/`, zero in the Go backend (`datatug-core`,
   `datatug-cli`), zero in demo data, zero in docs.
2. `ISqlWidgetSettings.db` / `.env` / `.hideColumns` were read only by
   `SqlQueryWidgetComponent`
   (`libs/datatug/main/src/lib/board/ui/components/widgets/sql-query-widget/`).
   That component was instantiated by no template: the `@case ('SQL')` block
   in `board-widget.component.html` has been commented out since the
   2026-03-04 migration commit `1726f96`. Zero in Go, zero in demo data.
3. `IBoardDef.parameters` was read by `board-page.component.ts`, but
   `boards.go`'s `Board` struct has no `parameters` field (it is
   `ProjectItem` + `rows`) — `ProjBoardBrief` in the same Go file carries
   `parameters` and `requiredParams` instead.
4. `DatatugBoardService.getBoard()` always returned
   `throwError('not implemented ...')`, so no board reached the rendering
   tree at runtime; the whole board UI was unexercised.
5. `ISqlWidgetSettings extends ICommandDefinition` (requiring `id`, `type`,
   `title` on widget settings) had no basis in `boards.go`, and
   `board-widget.component.ts` cast `widget.data` to `ISqlWidgetSettings`
   even though the local `ISqlWidgetDef.data` was `{ sql: ISqlWidgetSettings }`
   — internally inconsistent, confirming nothing exercised it.
6. The demo board
   (`datatug-demo-projects/demo-project-1/boards/board1/board.json`) is
   `{"title": "1st board"}` — no rows, no widgets.

### What changed

Removed:

- The seven files under `libs/datatug/main/src/lib/models/definition/board/`:
  `widget-def.ts`, `widget-http.ts`, `widget-name.ts`, `widget-sql.ts`,
  `widget-tabs-def.ts`, `widget-tabs.ts`, `widget.ts`.
- The three wire-schema interfaces from `board.ts`: `IBoardDef`,
  `IBoardRowDef`, `IBoardCardDef`.
- Five dropped fields, each because it had zero readers or was reachable
  only through dead code (see evidence above): `description`,
  `related.boards`, `db`, `env`, `hideColumns`.

Stayed, and why:

- `IBoardContext`, `IWidgetPosition`, `IBoardWidgetInstance` stayed in
  `board.ts` — they are UI-local state with no `boards.go` equivalent.
- `IParameterDef` in `models/definition/parameter.ts` stayed as-is — it
  mirrors `parameters.go`, not `boards.go`, and is what
  `ParameterLookupService` consumes.
- `GridWidgetComponent.hideColumns` stayed — it is a grid UI input, not part
  of the board schema.

`IProjBoard` (`libs/datatug/main/src/lib/models/definition/project.ts`) now
mirrors `ProjBoardBrief` field for field (`IProjItemBrief` +
`parameters?: IParameterDef[]` + `requiredParams?: string[][]`).

### Open questions for `boards.go` (datatug-core)

The following are the coordinating agent's observations, **not** a founder
ruling — both are tracked in the DataTug hub Feature
(`datatug/datatug` → `spec/features/dashboards`, "Open Questions"):

- `Board` carries no `parameters`, while `ProjBoardBrief` in the same file
  carries `parameters` and `requiredParams`; a `board.json` with
  `parameters` is silently dropped on a `LoadBoard`/`SaveBoard` round trip.
  Should `Board` carry them?
- `SQLWidgetSettings` is `{ query }` only, so a SQL widget has no db/env
  execution target, although `ParameterLookup` beside it does carry `db`.
  How is a board SQL widget meant to be executed? The dashboards Feature's
  REQ `board-persistence-and-query-binding` binds widgets to a library query
  plus parameters, which may make db/env a property of the bound query
  rather than the widget.
