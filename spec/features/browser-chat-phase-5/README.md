# Feature: Browser Chat Phase 5 FK JOIN exploration

## Summary

Discover and apply deterministic FK JOIN candidates from browser Chat result grids.

## Problem

Browser Chat can show a single-source Chinook result but cannot follow its actual foreign keys. A user must ask the model for another query, and the current browser DALgo dependency predates the shared recursive DTQL JOIN support. Browser IndexedDB has no native FK catalog, so discovery needs versioned metadata from the pinned Chinook source schema.

## Behavior

### Discovery and identity

#### REQ: fk-edges

The browser uses a checked-in FK manifest generated by `tools/generate-chinook-chat-schema.mjs` from the same pinned Chinook SQLite database and SHA-256 (`f82efedb6c5c40734609e168bc5be5616a2eca6b90ed0048451a8674625e03a3`) as the row fixture. Its content/version ID and source revision are explicit. Each FK ID is the schema-qualified child table, ordered child fields, parent table and ordered parent fields; a composite key is one edge. Discovery is deterministic, bidirectional, bounded by the relation instances already in the validated DTQL tree, and makes no AI call or recursive graph traversal. A `RelationInstanceId` is the ordered index path from the root `from` node (root `[]`, first child `[0]`), paired with its alias; `JoinCandidateId` is that instance ID, FK ID and direction. A new JOIN is appended to that exact node's `joins` array. Alias allocation uses the target table name, then `_2`, `_3`, etc. against all aliases in the tree. Only an active JOIN whose source node, target node and complete ordered ON field pairs match the candidate is suppressed for that source; repeated targets, distinct FKs, self-FKs and cycles remain available. Cardinality and exact fields are inspectable. Multiple FKs to one target show their source fields in the compact label.

#### REQ: browser-navigation

The result's candidate area supports pointer selection and keyboard focus: Up/Down choose a source row, Left/Right choose an edge, Enter opens details in the Selected workspace, Space applies the focused edge, and Escape returns focus to the result grid. Native grid/composer keyboard handling takes precedence while those controls have focus. Empty candidate state is compact. Applying a JOIN shows pending/error state and prevents a second application until the first settles.

### Application and execution

#### REQ: shared-join-action

A single application operation receives a session-scoped parent RecordSet ID and candidate ID, rechecks the current FK manifest and parent query, derives one recursive DTQL JOIN with deterministic ON predicates and collision-safe alias, validates it with the shared DALgo parser, then executes through the shared DALgo joined-query entrypoint. This requires pinning the merged `@dalgo/core` recursive JOIN revision and supplying an app-level `resolveSource` callback that maps each validated `main.Table` relation to the existing IndexedDB `QueryExecutor.query(StructuredQuery)` scan. It never merges displayed rows directly or accepts an AI-generated ON clause. It qualifies inherited filters and ordering when needed. It preserves existing output column IDs, makes each new target field's ID `<alias>.<field>` (with a deterministic numeric suffix only on a collision), and keeps display labels separate from IDs; this leaves existing View/Selection column references stable. An existing explicit projection is retained and extended, while an implicit projection is made explicit before joining. The SQL tab renders equivalent read-only SQLite syntax from the validated query.

#### REQ: durable-lineage

The resulting query and immutable RecordSet are saved through the existing DALgo session database. Their lineage records parent RecordSet, exact applied FK ID/direction/field payload, source/target aliases, FK-manifest version, derived DTQL, execution timing and output schema. Reload restores the snapshot without rerunning historical queries and recomputes candidates against current FK metadata. A stale or removed FK fails visibly and refreshes candidates. Existing Views, Selections, attachments, docks and Phase 4 bookmarks/tags continue to refer to RecordSet IDs. Clearing or deleting a session removes its joined results with existing session rules; switching projects cannot expose them.

#### REQ: agent-route

An agent request to join a named relation or field is resolved against the latest successfully executed RecordSet in the active session, unless the request names an exact in-session RecordSet ID. The interpreter may return only `{joinCandidate:{recordSetId,candidateId}}`, with opaque candidate ID selected from metadata provided in its prompt, never ON or target-only text. The browser re-resolves both IDs against the current session and calls the same application operation. Zero matches and ambiguous targets produce a structured list of choices without execution; the model never guesses an edge. The provider receives only candidate metadata and RecordSet IDs, not raw row/cell values.

#### REQ: safe-removal

Space applies an available edge. The browser does not remove an active JOIN in this phase because dependent SELECT, filter, order and nested JOIN clauses may reference it; active edges are omitted from candidate lists. A future removal action must validate dependencies before execution. This is an explicit add-only control, not a silent toggle.

### Scope

Foreign keys are the sole evidence source. Project/entity mappings, ModelSpec, inferred relationships, confidence ranking, automatic traversal, graph views, join-type editing and model-generated ON clauses are outside this phase. The web UX is adapted from the attached terminal brief; no terminal UI is changed.

## Acceptance Criteria

### AC: fk-discovery

Given a validated query with aliased, repeated and nested relation instances, when discovery runs, then each instance has its own exact FK edges in both directions, active edges alone are suppressed, and no candidate is inferred without FK metadata. Synthetic fixtures cover two FKs to one target, composite keys, self joins and cycles.

### AC: keyboard-details

Given a result grid with candidates, when the user navigates by keyboard or pointer, then each source and edge can be focused, details expose exact fields/evidence/cardinality, Space applies the selected edge once, and Escape returns focus to the grid without hijacking composer typing.

### AC: valid-join

Given an Invoice result and its Customer FK candidate, when the user applies the edge, then the derived DTQL validates, its ON uses `Invoice.CustomerId = Customer.CustomerId`, DALgo executes it against the browser's real Chinook tables, and the joined grid contains correctly matched rows and unambiguous columns.

Given the upgraded DALgo core and existing IndexedDB adapter, when a recursive joined query is executed, then each relation is scanned through the adapter's structured-query contract and the shared DALgo executor performs the JOIN; no UI row merge occurs.

### AC: chain-and-lineage

Given the joined result, when the user joins a further FK candidate, then candidates are recalculated for every participating instance and a new immutable RecordSet records both its direct parent and applied edge payload/manifest version. A reload, including after manifest drift, restores the saved data and lineage without execution. Existing View/Selection references keep their column IDs.

### AC: agent-ambiguity

Given two Address FKs or two relation instances that match a target name, when an agent asks to join Address without an exact edge, then no JOIN is executed and the choices are shown. Given one unique candidate, the agent route produces the same derived DTQL and result as the UI action.

### AC: lifecycle-and-failure

Given stale FK metadata, a changed project, a deleted session, or a canceled/failed application, when a JOIN is attempted, then the browser keeps prior snapshots intact and presents a clear error. Session clear/delete and existing View/Selection/dock workflows remain valid for joined RecordSets. Phase 4 bookmarks/tags must also resolve joined RecordSets before release.

### AC: browser-proof

Deterministic unit tests, browser E2E with real IndexedDB Chinook data, production build/lint, independent review, and the repository's required checks pass before release. The local trial and production deploy are reported as separate receipts.

## Open Questions

Browser Phase 4 bookmarks and tags are absent from current `main`; Phase 5 release is blocked until they are included or landed and the joined-RecordSet lifecycle check passes.
